# Этапы 7–8: правила, эффект и демонстрация

`configs/ecology_v1.json` задаёт `retention_days_by_category` (целое число дней для категории), `dark_days`, `cost_per_gib_month` в валюте `currency`, `kwh_per_gib_month`, а также доли стоимости и энергии архива относительно активного хранения. Сроки по умолчанию пусты, а удельные коэффициенты равны `null`: система не придумывает локальную политику и тарифы. Нулевое значение коэффициента допустимо лишь если организация действительно ввела нулевое допущение. Значение `archive_*_fraction=1` означает отсутствие экономии от переноса. Изменение политики требует изменения JSON и перезапуска сервиса для воспроизводимого прогона.

`GET /api/ecology` показывает истёкшие сроки, кандидатов на удаление/архив, рекомендации снизить дублирование и проверить доступ/цель обработки для файлов с обнаруженными ПДн. Экономический блок: базовая стоимость = (известные активные байты + известные архивные байты × доля стоимости архива) / 2³⁰ × цена за ГиБ в месяц; базовая энергия аналогично. При неизвестном размере базовая оценка `null`. Прогноз удаления = сумма размеров уникальных рекомендованных файлов. Перенос в архив не уменьшает общий физический объём: для него показаны перемещённые байты, а стоимость и энергия уменьшаются лишь на заданную разницу удельных коэффициентов. Прогноз стоимости/энергии = удаляемые байты × активный коэффициент + архивируемые байты × активный коэффициент × (1 − доля архива). При неизвестном размере кандидата прогноз `null`. Эти значения **оценочные**, зависят от размера, дедупликации, цены, энергии, принятия рекомендаций, сохранения резервных копий и фактической политики хранения. Снижение риска ПДн в деньгах или кВт·ч не оценивается. ПДн-детектор выдаёт кандидатов, не юридическое заключение.

Архивируется только файл, зарегистрированный сканированием и повторно сверенный по SHA-256. `POST /api/objects/{id}/archive` доступен администратору; файл перемещается в `var/archive/<id>/<sha256>` (относительно каталога `cache_path.parent`), а запись и `file_archive` фиксируются в одном действии с откатом переноса при ошибке базы. Архив должен быть на том же томе, что источник: перемещение через разные тома отклоняется. Появление нового файла по уже архивированному или удалённому пути при сканировании вызывает конфликт; сначала требуется ручное разрешение идентичности записи. Обычное удаление записи API не удаляет архивную запись. `POST /api/objects/{id}/delete-file` доступен только администратору, только после архивирования. Тело: `{"expected_sha256":"<полный SHA-256>","confirmation":"DELETE <id> <полный SHA-256>"}`. Перед удалением хеш проверяется ещё раз. Журнал сначала фиксирует `file_delete_pending`, затем `file_delete`. При сбое удаления остаётся `deletion_pending` и действие можно повторить с тем же подтверждением. Это логическое удаление файла, не гарантированное физическое стирание носителя. `recorded_archive_file_bytes_removed` суммирует удалённые файлы в архиве по уникальным ID; фактическое освобождение физических блоков остаётся `null`, если были удаления, поскольку копии и жёсткие ссылки не учтены. Прежние резервные копии сохраняют содержимое и должны управляться отдельной политикой. `GET /api/audit` показывает журнал администраторам и аудиторам.

`POST /api/backups` с `{"kind":"full"}` создаёт полную копию каталога SQLite через online backup API и всех управляемых присутствующих/архивных файлов. `{"kind":"incremental","parent_id":"<id>"}` создаёт новый полный снимок метаданных и сохраняет только новые/изменившиеся файлы, ссылаясь на неизменные blobs предка. Каждая копия имеет `manifest.json`, его SHA-256, SHA-256 снимка БД и SHA-256 каждого файла. Для восстановления нужна вся цепочка, начиная с полной копии; удаление любого предка делает потомков невосстановимыми. SHA-256 выявляет повреждение, но не подмену злоумышленником, который может переписать манифест и его контрольную сумму; для такой угрозы нужны подпись и защищённое внешнее хранилище. Копии содержат исходные документы и требуют ограниченных прав доступа, шифрования носителя и отдельной политики хранения. Встроенного шифрования и автоматической очистки копий пока нет. Копируются только управляемые файлы каталога; `metadata_only` не содержит оригинала.

`POST /api/backups/{id}/restore` восстанавливает в **новый** `var/restores/<id>`: там находятся `catalog.sqlite3`, `source/`, `archive/`. Все манифесты, снимок БД и blobs проверяются до публикации каталога; восстановление сначала собирается во временной директории и публикуется одной операцией переименования. Существующие файлы и рабочая база не перезаписываются. После проверки администратор отдельно решает, когда переключить сервис на восстановленные пути. Это снижает риск потери текущего состояния и сохраняет согласованность метаданных с файлами в восстановленном комплекте.

Сценарий демонстрации на тестовом каталоге (не на документах организации):

1. Запустить `python -m app.api.main init-db`, затем `serve`, установив `PII_SOURCE_ROOT` на отдельную папку с двумя тестовыми TXT-файлами и `PII_DATABASE_URL` на тестовую SQLite-базу. Войти администратором.
2. Вызвать `POST /api/sources/scan`, проверить `GET /api/objects` и `GET /api/ecology`. Задать тестовые сроки/коэффициенты в `configs/ecology_v1.json`, повторить отчёт и записать допущения.
3. Создать полную копию через `POST /api/backups`, сохранить её `id`; изменить или добавить TXT-файл и повторить сканирование.
4. Архивировать один объект через `POST /api/objects/{id}/archive`; создать инкремент с `parent_id` полной копии. Вызвать `POST /api/backups/{incremental_id}/restore`; сравнить SHA-256 двух восстановленных файлов и значения `availability` в восстановленной БД.
5. Проверить, что удаление с неверным `confirmation` возвращает 409. Отправить точное подтверждение для архивного объекта, затем проверить `GET /api/audit`, `GET /api/ecology` и отсутствие архивного файла. Восстановленный из предыдущей копии комплект остаётся неизменным.
6. На **копии тестового backup-хранилища** испортить один blob и убедиться, что восстановление отклонено и каталог назначения не появился. Автоматизированный вариант этого сценария: `tests/integration/test_system.py::test_archive_backup_restore_and_confirmed_delete`.
